## 2. 動作仕様

| | 右回転 | 左回転 | 押し込み |
|---|---|---|---|
| **PROFILE 1 YOUTUBE**（1bと同じ） | 1目盛りごとに `.`（0x37） | 1目盛りごとに `,`（0x36） | `k`（0x0E）を1回 |
| **PROFILE 2 MOUSE**（1cで追加） | マウス右移動（カウンタ差分×4） | マウス左移動（カウンタ差分×4） | **左ボタン：押している間は押下、離すと解放** |

- 切替は1bと同じく `Fn+1`／`Fn+2`。本体キーはMacに送らない。起動時は PROFILE 1。
- 移動量：1目盛り＝カウンタ±2＝マウス±8カウント（`MOUSE_GAIN = 4`、仮の値）。Y、ホイール、パンは常に0。
- 回転方向：右回転でカウンタが＋になることはv2で実測済み。それがMac画面上で右への移動になるかは ❓（§7で確認）。

### 画面表示

```
USB HID READY                ← 文字サイズ2
PROFILE 2 MOUSE              ← 1は「PROFILE 1 YOUTUBE」
VAL 124 R+0
BTN UP X+96                  ← PROFILE 2：ボタンの状態、送信が確認できたX移動の合計
                               （PROFILE 1では 1b と同じ「.12 ,8 k3」）
MOUSE DOWN                   ← 最後のイベント（黄）
BTN raw=1  Q0/0 OVF0         ← ここから文字サイズ1
FAIL0 SKIP0 ERR0
W14 T3
KB keys=0 fn=0 chg=1
MS host=0 want=0 rep12 fail0 clip0      ← 1cで追加
```

`MS` 行の意味：
- `host`：送信が確認できた最後のレポートのボタン状態
- `want`：いまMacに見せたいボタン状態
- `rep`：送信が確認できたマウスレポートの数
- `fail`：結果不明のマウスレポートの数
- `clip`：上限を超えて捨てた移動量
- `SYNC`：ボタン状態の再送待ち

**`host=1 want=0` が続く場合は、解放が届いていない可能性がある。**

## 5. ソース確認

### 5-1. 複合HIDの構成：「USBHIDMouseを先に宣言するだけで十分か」

**結論：ソース上、`USBHIDMouse` を先に宣言すれば、HIDインターフェースはブートプロトコルなしになる。ただし、それが成り立つのは「同じスケッチ内に、マウスより先に構築される別の `USBHID` オブジェクトがない」場合に限られる。**

1bには送信用の `USBHID hidOut(HID_ITF_PROTOCOL_KEYBOARD)` があった。これをそのまま残してマウスより前に置くと、インターフェースはブートキーボードになる。

そこで1cでは、**`hidOut` をプロトコルなし（`HID_ITF_PROTOCOL_NONE`）にして最初に宣言した。** これにより、マウスとキーボードの宣言順に関係なく、プロトコルなしに決まる。マウス→キーボードの順は公式例 `KeyboardAndMouseControl.ino` と同じにしてある。

**根拠：** インターフェースのプロトコルは、最初に構築された `USBHID` が決める（`USBHID.cpp:277-287`。2つ目以降の構築では、static変数 `tinyusb_hid_devices_is_initialized` のため何もしない）。グローバルオブジェクトは、同じファイル内では宣言順に構築される（C++の規則）。

**他のファイルに `USBHID` のグローバルオブジェクトがないこと：** コア、USBライブラリ、M5Cardputer、M5Unified、M5GFX、M5Unit-Encoder を検索した。見つかったのは、各HIDクラスのメンバー（`USBHID hid;`）だけで、グローバルオブジェクトはなかった。✅

**初期化の順序（`MediaJog_1c.ino` の宣言順）：**

| 順 | 時点 | 処理 | ソース |
|---|---|---|---|
| 1 | 静的初期化 | `USBHID hidOut(HID_ITF_PROTOCOL_NONE)`：最初の `USBHID`。プロトコル＝NONEを記録し、`tinyusb_enable_interface2(USB_INTERFACE_HID, …, reserve_endpoints=false)` でHIDインターフェースを**1つ**予約する | `USBHID.cpp:277-287` |
| 2 | 静的初期化 | `USBHIDMouse UsbMouse`：メンバー `hid()`（既定値NONE、`USBHID.h:75`）は何もしない。`addDevice(this, 相対マウス記述子の長さ)` で記述子を登録 | `USBHIDMouse.cpp:28-33` |
| 2a | 〃 | 記述子の情報は、別ファイルのグローバル `HIDMouseRel`（定数のみで構成）から読む。定数初期化のため、静的初期化の順序に左右されない | `USBHIDMouse.cpp:96-98` |
| 3 | 静的初期化 | `USBHIDKeyboard UsbKeyboard`：メンバー `hid(HID_ITF_PROTOCOL_KEYBOARD)` は、すでに初期化済みのため**何もしない**（プロトコルはNONEのまま）。`addDevice` でキーボード記述子を登録 | `USBHIDKeyboard.cpp:35-42` |
| 4 | `app_main` | CDC On Boot により `Serial.begin()` と `USB.begin()`。`tusb_hid_load_descriptor()` がインターフェース記述子を出力する | `main.cpp:99-110`、`USBHID.cpp:194-216` |
| 5 | ホストからの要求時 | `tinyusb_load_enabled_hid_devices()` が、`addDevice` の順（マウス→キーボード）にレポート記述子を連結し、`esp_hid_parse_report_map()` で検査する | `USBHID.cpp:153-192` |
| 6 | `setup()` | `UsbMouse.begin()`、`UsbKeyboard.begin()`：共有の送信用セマフォを作る（2回目は何もしない） | `USBHID.cpp:289-296` |

**インターフェース記述子**（`TUD_HID_INOUT_DESCRIPTOR`、`usbd.h:355-361`）：

| 項目 | 1a・1b（ブートキーボード） | 1c |
|---|---|---|
| bInterfaceClass | HID | HID |
| bInterfaceSubClass | 1（Boot） | **0** |
| bInterfaceProtocol | 1（Keyboard） | **0（None）** |
| エンドポイント | キーボード用に予約したEP 1（IN/OUT） | 空いているエンドポイントを割り当て（`USBHID.cpp:202-205`） |
| bInterval | 1 | 1 |
| レポート記述子の長さ | キーボード分 | マウス＋キーボードの合計 |

**Report ID：**

| ID | 装置 | レポート本体 | 記述子 |
|---|---|---|---|
| 1 | キーボード | `hid_keyboard_report_t`（8バイト：修飾、予約、キー×6） | `TUD_HID_REPORT_DESC_KEYBOARD` |

- プロトコルがNONEのため、`SendReport()` は常にReport IDを付けて送る。Report ID 0への置き換え（`USBHID.cpp:343-345`）は起きない。
- 送信はすべて `hidOut.SendReport(ID, …)` で行い、成否を確認する。`USBHIDMouse::move()` などのライブラリAPIは使わない。

**1bからの変化（実機で影響を確認する）：**
- ❓ インターフェース記述子が変わるため、Macが新しいデバイスとして認識し直す可能性がある。キーボード設定アシスタントが再び表示される可能性もある。
- ブートプロトコルを必要とする環境（BIOSなど）では、キーボードとして使えなくなる。本プロジェクトの用途（macOS上のアプリ）では使わない。
- ❓ macOSが、マウス＋キーボードの複合レポートを期待どおり扱うか。

### 5-2. マウスボタンの押しっぱなし防止

**原則：**
- **ボタンのレポートは「状態」を送るので、同じ状態を何度送っても害がない。** そのため、ボタン状態は、送信が確認できるまで再送する。
- **移動量は相対値なので、結果不明のレポートは再送しない**（移動が二重になるのを避けるため）。

**状態変数：** `mouseWanted`（Macに見せたい状態）、`mouseHost`（送信が確認できた最後の状態）、`mouseSyncNeeded`（ボタン状態の再送が必要）。

| 出来事 | 処理 |
|---|---|
| PROFILE 2で、USB準備完了中にノブを押した | `want=1` |
| ノブを離した（どのプロファイルでも） | `want=0` |
| PROFILE 2で、USB未準備のときにノブを押した | 何もしない（`SKIP` に数える）。後でUSBが準備完了になっても押下にはしない |
| プロファイルの切替 | `want=0`、再送フラグを立てる。未送信のキー操作と移動量は破棄する |
| U135の通信喪失（500msごとの確認でACKなし） | `want=0`、移動量を破棄する |
| U135の一時的な読み取り失敗 | 直前のボタン状態を保持する（押していれば押したまま）。通信が続けて失われた場合は、500ms以内の確認で上の「通信喪失」になる |
| USBが未準備になった（切断、サスペンド） | `want=0`、移動量を破棄する。**この間はレポートを送れない** |
| USBが準備完了になった（再接続、復帰） | 再送フラグを立てる → 最初のマウスレポートは**ボタン解放（want=0）**。キーボードも全キー解放から始める（1bと同じ） |
| 再接続時にノブを押したままだった | 押下にしない。押下にするには、一度離して押し直す必要がある |
| 送信の結果不明 | 再送フラグを立て、次のループでボタン状態を再送する |
| `hidOut.ready()` が偽 | 何も送らず、状態と移動量を保持して次のループで再試行する |

送信の順序は、マウス（解放を含む）→キーボードの順（`loop()`）。

**USB切断中に解放レポートを送れない場合：**
- **ケーブルを抜いた場合：** Macから見てデバイス自体がなくなる。HIDホストは、取り外された装置の押下状態を保持しないのが一般的だが、**macOSでの実際の挙動は未確認（❓）**。
- **サスペンド（Macのスリープ、または電池駆動中に抜いたときにサスペンドとして見える場合）：** レポートは送れない。Cardputer側では `want=0` にしておき、復帰後の最初のレポートで解放を送る。サスペンド中にMacがボタン押下を処理し続けるかは ❓。
- **どちらの場合も、再接続後に、ノブの古い押下が押下として送られることはない。**

**残るリスク：** 押下のレポートが届いた後、USBが「準備完了」のままですべての送信が失敗し続けた場合は、Macではボタンが押されたままになる。画面に `host=1 want=0 SYNC` と表示される。対処はUSBケーブルを抜くこと（§8）。

### 5-3. 移動量の扱い（PROFILE 2）

- カウンタの差分×`MOUSE_GAIN`（4）を、未送信の移動量に加える。毎ループ、最大4レポート（1レポートあたり最大±127、合計±508／ループ）まで送る。
- 未送信の移動量の上限は±1,016（127×8）。超えた分は捨てて `clip` に数える。
- USB未準備のときの回転は加えない（`SKIP` に数える）。
- `MOUSE_GAIN = 4` は仮の値。Finderでの試験は「向き」と「機能」の確認が目的で、移動量はmacOSのポインタ加速の影響を受ける。

### 5-4. 第1bからの変更点（PROFILE 1への影響）

- 変更点：
  - HIDオブジェクトの宣言（`hidOut` をNONEにして先頭に移動、`UsbMouse` を追加）
  - マウス用の変数と関数
  - 回転・ボタン処理を `onRotation()`／`onButton()` に分離
  - `setProfile()` の追加（切替時の後始末）
  - 画面の `PROFILE n YOUTUBE/MOUSE` と `MS` 行
  - `setup()` に `UsbMouse.begin()` を追加
- U135の読み取り、キーボードの送信（`tapKey`／`sendQueued`／解放の再送）、`Fn` の検出、`M5.begin()` の設定は1bと同じ。

## 7. 実機試験手順（第1c-1：MacのFinderのみ。RetroArchは行わない）

1. LauncherのWi-Fiアップロードで `MediaJog_1c/build/MediaJog_1c.ino.bin` を転送し、起動する。
   - 画面が点かない場合は中止して§8へ。
2. **USBを挿す前に：** `PROFILE 1 YOUTUBE`、`VAL`、`ERR0`、`MS host=0 want=0` を確認する。
3. **USBを接続：** `USB HID READY` を確認する。
   - 初回認識が不安定な場合は、REPORT.md §18 の項目（接続の順序、画面1行目の表示、READYまでの時間と操作、ケーブルとポート、システム情報のUSB欄）を記録する。
   - 新しいデバイスとして認識された、キーボード設定アシスタントが出た、などの変化も記録する。
4. **PROFILE 1の回帰確認（短く）：** テキストエディット（ABC入力）で、右→`.`、左→`,`、押し込み→`k` が入力される。
5. `Fn+2` → `PROFILE 2 MOUSE`。テキストエディットからFinderに切り替える。
6. **移動：**
   - 右にゆっくり回す → ポインタが**右**に動き、画面の `X` が増える。
   - 左に回す → 左に動き、`X` が減る。
   - 上下には動かないこと。
   - 右回転と左移動が逆になっていたら記録する。
7. **クリック：** 試験用フォルダ内のファイルにポインタを合わせ、ノブを押して離す → ファイルが選択される。画面は `BTN DOWN` → `BTN UP`、`MS host` も1→0。
8. **ドラッグ：** 試験用フォルダ内のファイルにポインタを合わせ、**ノブを押したまま回す** → ファイルが横に引きずられる。離す → その場所でドロップされる（フォルダ内での位置変更）。
9. **押しっぱなし防止の確認：**
   - a. **プロファイル切替：** ドラッグ中（ノブを押したまま）に `Fn+1` → ドラッグが終わる（ボタン解放）。画面は `PROFILE 1`、`MS host=0 want=0`。その後ノブを離しても、`k` が入力されたり何かが起きたりしないこと。
   - b. **USB切断：** ドラッグ中にUSBケーブルを抜く。
     - Macでドラッグが続いていないこと（❓macOSの挙動）。
     - 画面1行目が `NOT MOUNTED` か `SUSPENDED` のどちらになったかを記録する。
     - ノブを押したままケーブルを挿し直す → ボタンは押されないこと（`want=0`）。ノブを一度離して押し直すと押下になる。
   - c. **U135の通信喪失：** 動作中にGroveケーブルを抜く試験は、**今回は行わない**（これまでの手順はすべて「電源OFFで接続」としてきたため）。必要かどうかはエドガーと判断する。
10. `Fn+1` → PROFILE 1に戻し、YouTubeでコマ送り・コマ戻し・再生／停止を1回ずつ確認する（任意）。
11. 記録：画面の写真、`MS host/want/rep/fail/clip`、`SYNC` の有無、`ERR`／`FAIL`／`SKIP`／`W`／`T`、USB初回認識の状況。

**1c-1合格条件：**
- PROFILE 2で、Finderのポインタ左右移動、クリック、ドラッグが動作する。
- 9-a・9-bで押しっぱなしにならない。
- PROFILE 1のキー入力が維持される。

| Macでマウスボタンが押されたまま（ドラッグが終わらない） | **USBケーブルを抜く**。画面の `MS` 行（`host`／`want`／`SYNC`）を先に記録できればする。補足：解放の再送はプロファイルに関係なく毎ループ自動で行われる。PROFILE 2であれば、ノブを押して離すと状態の送信がもう一度起きるが、PROFILE 1でノブを押すと `k` が入力されるので行わない |
| Macでキーが押されたまま | USBケーブルを抜く |
| 本体キーでMacに入力が起きた | 直ちに中止して記録する（設計上は起きないはず） |
| 画面が点かない、または操作できない | 電源OFF→ON。Launcherに戻り、**第1b成功版**を起動する |
| Launcherに戻れない | 作業を止めて相談する（G0ダウンロードモードでのLauncher再書き込みは今回の範囲外） |

## 9. レビューで確認してほしい点

1. §5-1：`hidOut(HID_ITF_PROTOCOL_NONE)` を先頭に宣言して、プロトコルを宣言順に依存させない構成。マウス→キーボードの記述子の順。
2. §5-2：ボタン状態を確認できるまで再送し、移動は再送しない方針。USB未準備中の押下を無視し、再接続後は押し直しを必要とする扱い。
3. プロファイル切替時に、未送信のキー操作と移動量を破棄すること。
4. `MOUSE_GAIN = 4`、1ループ最大4レポート、未送信の移動量の上限±1,016（いずれも仮の値）。

### 10-2. USB切断・再接続試験（時系列どおり）

**試験A：USB切断後にLauncherが起動したケース**

1. PROFILE 2でドラッグ。
2. USBケーブルを抜く。
3. USBケーブルを再接続。
4. Launcherが起動。
5. Mac側ではドラッグが解除されていた。

判定：MediaJogが動作を続けていないため、**MediaJog自身の再接続処理が成功したとは判定しない。** この試験での物理電源スイッチの状態は記録されていない。

**試験B：Cardputer ADVの物理電源スイッチをONのまま維持したケース**

1. PROFILE 2でドラッグ。
2. USBケーブルを抜く。
3. 画面表示が `USB SUSPENDED` に変化。
4. USBケーブルを再接続。
5. 表示は `USB SUSPENDED` のまま。
6. Mac側でドラッグは再開されなかった。
7. Cardputer ADVの物理電源スイッチをOFF→ON。
8. 表示が `USB HID READY` に復帰。
9. `PROFILE 1 YOUTUBE` に戻り、ドラッグ状態も解除されていた。

**判定：**
- USB切断時にMac側のドラッグが解除されることは、実機で確認できた。
- **USBの再接続だけでは `USB HID READY` に復帰しなかった。**
- 電源の再投入による復帰は確認できた（再起動のため PROFILE 1 に戻る）。
- MediaJogが再接続を検知して解放レポートを送る処理（§5-2）が成功するかは、**確認できていない**（再接続後に準備完了の状態にならなかったため、その処理が実行される場面がなかった）。
- **USBの自動復帰不良の原因は未特定。**

**画面表示についてソースから言えること（原因の断定ではない）：**
- `USB SUSPENDED` は、`(bool)USB`（開始済みかつ `tud_mount_cb` 以降マウント状態）が真で、本スケッチの `usbSuspended` フラグが真のときに表示される（`MediaJog_1c.ino` の `drawStatus()`）。
- このフラグは、TinyUSBのサスペンドイベントで立ち、レジューム、マウント（STARTED）、アンマウント（STOPPED）のいずれかのイベントで下りる（`onUsbEvent()`、`USB.cpp:99-130`）。
- したがって試験Bの手順5では、再接続後にこの3つのイベントのいずれもスケッチに届いていなかったことになる。
- **なぜ届かなかったか（TinyUSB側で再接続が検出されなかったのか、Mac側の列挙の問題か、など）は未調査。** 試験Bで再接続後にMacの「システム情報」→「USB」にデバイスが表示されていたかは記録されていない。
